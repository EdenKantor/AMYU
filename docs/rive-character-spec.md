# Rive character specification

Desktop V1 uses Rive. The artwork is replaceable; the semantic avatar contract is stable. A final original `.riv` asset is an external art deliverable and has not been created in this foundation milestone.

## Required production rig

Provide one documented artboard and one main state machine, normally `AMYU_Main`. The application semantic API and Rive asset inputs are separate contracts. The adapter alone owns artwork names and types. Missing or wrong-type optional controls report `UNMAPPED` and continue rendering; a bad file or missing artboard produces a recoverable load error. A partial rig must never be advertised as fully supported.

| Group | Required controls |
| --- | --- |
| Body | Body lean X/Y, head rotation X/Y, head tilt, breathing, bounce, anticipation, arm gestures, optional squash/stretch |
| Eyes | Openness, scale, squint, pupil/gaze X/Y, blink |
| Face | Mouth open, mouth width, smile, frown, optional brows |
| State | Idle, listening, thinking, speaking, acting, sleeping |
| Affect | Every semantic emotion with continuous intensity |
| Gestures | Wave, nod, shake head, head tilt, bounce, celebrate, shrug; private local sleep/wake timing |

Inputs should be continuous wherever appropriate. Expressions must interpolate instead of popping. The rig should distinguish intensity 0.35 from 0.95, allow head and eye movement independently, and compose a blink or breathing with speaking. It should return to stable idle after one-shot gestures.

The checked-in target adapter is `createProductionRig` in `packages/avatar-rive/src/production.ts`. Defaults are artboard `AMYU` and state machine `AMYU_Main`; the target has 18 numeric controls, 5 booleans and 10 triggers. Visual support starts unknown until the actual asset and behavior are verified, while visemes default unsupported. Input aliases, artboard and state-machine names are configuration; changing them does not affect Core.

| Type/range | Target properties |
| --- | --- |
| Number, -1..1 | gazeX, gazeY, headYaw, headPitch, headTilt, mouthWidth, bodyLean |
| Number, 0..1 | eyeOpen, blinkOverride, mouthOpen, smile, frown, browUp, browDown, bodyBounce, speechEnergy, emotionIntensity |
| Number, 0..9 | emotion: neutral, happy, excited, curious, concerned, surprised, empathetic, amused, focused, confused |
| Boolean | isListening, isThinking, isSpeaking, isActing, isSleeping |
| Trigger | gestureWave, gestureNod, gestureShakeHead, gestureHeadTilt, gestureBounce, gestureCelebrate, gestureShrug, clickReact, wakeUp, goToSleep |

Idle has all state booleans false. Sleep/wake transitions edge-trigger their controls; gestures and click reactions trigger once per semantic request. The adapter converts frame mouth width from 0–1 into the production -1–1 range. Exact missing or wrongly typed mappings appear as `UNMAPPED` and downgrade the corresponding capability.

Prefer concurrent Life, Conversation, Face, Gaze, Speech and Gestures responsibilities. AMYU owns when behaviors occur; the Rive file owns their appearance. Do not author every combination as a separate animation, or add a second independent automatic blink loop that conflicts with AMYU's local schedule. An asset using ViewModel/Data Binding needs a renderer-side binding adapter; the current driver supports state-machine number, boolean and trigger inputs and introspects ViewModel properties without driving them.

`viseme` 0..14 is reserved for a future reviewed driver/asset. It is not implemented by this developer rig. The temporary prototype mascot is not the AMYU production identity.

## Developer asset

The checked-in `assets/character/amyu-developer.riv` is an original temporary vector character generated by `scripts/build-character.mjs`; no external artwork, fonts or images are included. It targets Rive format 7.0. Artboard and state machine are both named `AMYU Developer`. Run `pnpm character:build` to reproduce the binary and binding manifest.

The rig exposes 23 numeric blend controls: `bodyX`, `bodyY`, `bodyRotate`, `bodyScaleX`, `bodyScaleY`, `headX`, `headY`, `headTilt`, `gazeX`, `gazeY`, `eyeOpen`, `eyeScale`, `browRaise`, `browTilt`, `mouthOpen`, `mouthWidth`, `smile`, `leftArm`, `rightArm`, `armLift`, `feet`, `antenna`, and `shadow`. Exact ranges/defaults are in `assets/character/rig-manifest.json`; mapping from the renderer-independent `AvatarFrame` lives in `packages/avatar-rive/src/rig.ts`.

The developer rig composes continuous controls through a deterministic frame, rather than separate state/emotion input names inside the artwork. This is a supported development adapter choice, not a requirement that future production artwork use these same input names. Consult `assets/character/README.md` for provenance and limitations. The lab reports its readiness status. Do not mistake the development character for the final character design.

The current artwork must be consumed as a Rive asset with local runtime resources. Do not add remote asset fetches to make it work. A production swap must include the binary, artboard/state-machine names, binding manifest, license/provenance and visual acceptance record. See [asset strategy](avatar-assets.md) and [third-party provenance](third-party-assets.md).

## Introspection and capability evidence

The Rive 2.44 runtime can report actual artboards, state machines, numeric/boolean/trigger inputs, timeline animations and ViewModel properties. The API used here cannot enumerate the full state-machine state list or complete binding-target graph; those fields stay unknown. The original developer file has one artboard, one state machine, 46 timeline poses, 23 numeric inputs, zero booleans/triggers and zero ViewModels. Its seven gestures are composed through numeric poses, so no trigger input is invented for this file.

Developer gaze, blink, continuous mouth, emotion blend, head control and all seven gestures are verified supported; visemes are unsupported. Future third-party asset support stays unknown until inspection and visual review. A data-binding-only rig requires the appropriate adapter instead of assuming numbered state-machine inputs exist.

## Replacement procedure

1. Place the reviewed asset under `assets/character` (and expose it through each app's local asset route).
2. Supply `RiveAvatarRenderer.create` with the local `assetUrl` and a `RiveRigAdapter`; update only the adapter when artwork-specific names differ.
3. Introspect actual inputs and types. Display missing controls as `UNMAPPED` and downgrade capabilities; renderable does not mean production-ready.
4. Run the package tests, typecheck and production build.
5. Complete the visual acceptance checklist for every state, emotion, gesture, gaze extreme and mouth energy.
6. Complete a one-minute qualitative life check and a 30-minute soak on the target native webview.

No conversation, personality, memory, permission or provider code changes should be necessary for an artwork swap. The development adapter may expose a smaller temporary rig; any missing production controls must remain documented and may not be advertised as implemented.

## Speech

Mouth open follows smoothed normalized outgoing audio RMS in V0. Audio is the clock; no animation completion can delay playback. The `LipSyncDriver` boundary permits future visemes without changing the semantic controller. Manual lab energy demonstrates the mouth control; it is not proof of realtime provider or barge-in integration.
